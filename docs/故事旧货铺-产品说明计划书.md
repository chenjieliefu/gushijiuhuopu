## 一、创作思路：从“看完一个故事”到“参与一次相遇”

故事里的旧物，往往比它的价格更值得追问。一台相机为什么被留下？一张照片记录了谁？一个人为什么愿意把珍视的物件交到别人手里？这些问题天然连接着人的经历、情绪与选择。

《故事旧货铺》把旧货店作为叙事空间：玩家成为店主，接待带着旧物前来的角色。通过查看物件、听取讲述和主动提问，玩家逐渐理解旧物背后的人，再决定是否接收寄展。旧物留在柜子里，故事则进入收藏册。

我们希望创造一种温暖、安静、可以由玩家掌握节奏的体验。它不要求复杂操作，也不依赖持续播放的视频。图像负责建立氛围，文字负责讲清故事，声音和轻量动态补充情绪，交流则让玩家拥有参与感。

产品的长期方向，是让 AI 成为有身份、有动机、有知识边界的故事角色，在确定的故事事实下回应玩家的追问。**当前原型已完成一件旧物、一个篇章的完整体验，并接入受剧情约束的真实 AI 自由对话。**

## 二、产品定位与目标用户

**产品定位：以旧物为入口、以角色交流为连接、以收藏为情感收束的轻量互动叙事游戏。**

目标用户包括喜欢生活故事、情感叙事、角色扮演和轻度解谜的读者，以及希望将自己的作品转化为互动体验的故事创作者。

| 用户需求 | 产品回应 |
| :--- | :--- |
| 想短暂离开信息流，沉浸在一个完整故事中 | 以一间店、一位来访者和一件旧物构成独立体验 |
| 阅读时有疑问，希望继续追问 | 提供角色交流与推荐问题；后续接入有事实边界的 AI 自由问答 |
| 不喜欢文字自动跑过，也不希望全程只看静态页面 | 逐句点击推进，可切换自动阅读，并搭配场景变化与声音 |
| 希望体验结束后仍能回看有所触动的内容 | 将旧物与介绍收进可翻阅的收藏册 |

首版优先验证单篇体验是否完整、阅读节奏是否舒适、角色交流是否有参与价值，不以章节数量或复杂经营系统作为主要目标。

## 三、核心体验与玩法设计

### 3.1 一次完整的游玩流程

```text
主页 → 故事选择 → 进入旧货铺 → 看山来访 → 查看相机与照片 → 交流来意
    → 听取《遗失的晴天》 → 阅读后追问 → 确认接收寄展
    → 相机进入展柜 → 收藏册新增图案 → 点击查看介绍与故事
    → 返回主页 → 再次选择故事
```

| 环节 | 玩家操作 | 体验目标 |
| :--- | :--- | :--- |
| 来访 | 进入店铺，了解看山与旧物的关系 | 建立角色身份与本次来访的目的 |
| 查看 | 点击相机、照片，阅读物件信息 | 用具体物件引发好奇，形成进入故事的理由 |
| 交流 | 选择问题，了解寄展来意 | 让玩家成为交流的参与者 |
| 阅读 | 点击或按空格推进一句，按需自动阅读 | 把阅读速度交给玩家，避免被动等待或错过台词 |
| 追问 | 在故事结束后继续交流 | 回应玩家对人物经历和物品意义的疑问 |
| 寄展 | 独立确认接收，也可以暂缓决定 | 让收藏成为一次明确的选择 |
| 收藏 | 打开册子，点击相机图案查看介绍 | 将完成体验转化为可回顾的情感记录 |

### 3.2 采用 Galgame 式阅读，但保留旧货铺的空间感

主页不绑定具体篇章的物件，玩家先通过故事选择页进入篇章。故事完成后可返回主页，已保存的进度与收藏继续保留。

游戏以场景作为主要画面，人物与对话浮现在场景内部。玩家点击时，尚未显示完的文字会先完整显示；再次点击才进入下一句。系统同时提供自动阅读、台词重听、已读记录和隐藏文字等操作。

场景图随剧情切换，人物通过轻量动态获得呼吸感。背景音乐与旁白共同服务故事节奏，玩家可独立调节音量。主要游玩界面适应屏幕，减少上下滚动造成的沉浸中断。

### 3.3 收藏是一本册子，也是一处故事的归所

接收寄展后，相机会自然出现在店内展柜中。玩家点击展柜里的相机，或点击收藏入口，即可打开收藏册。

收藏册首先呈现相机图案，点击后翻到物品介绍，记录故事名称、物品主人、带来的人和相关经历。玩家还可以继续翻阅完整故事。首版只展示实际完成的相机篇章，不展示未经制作和确认的后续故事。

## 四、首个篇章：《遗失的晴天》

一台旧相机中留下了一卷未冲洗的胶卷。照片里明媚的女孩，与苏晚有着相同的面容。她沿着照片中的地点寻找，逐渐发现，那些看似陌生的影像，记录的正是自己遗忘的青春。

这个篇章围绕记忆、失落与重新感受生活展开。相机既是故事线索，也是情绪的载体：它保留下来的不仅是景色，还有一个人曾经如何看待世界。

在游戏中，看山受苏晚委托，将相机与照片带到旧货铺办理寄展。这个连接设定让玩家能够自然地接触故事，同时保持人物关系清晰：**看山是讲述与寄展的来访者，苏晚是物品主人，玩家是接收寄展的店主。**

当前章节包含 51 个逐句阅读单元。首版以完整阅读和寄展收藏为结束，尚未实现多结局或通过推理改变故事事实。后续若拓展分支，将先明确哪些选择只影响角色态度、哪些选择会改变结局，再进行内容制作。

## 五、适配知乎社区的场景价值

### 5.1 把“提问”变成进入故事的方式

项目与知乎场景的连接，首先体现在提问行为上。用户面对一段经历时，往往不仅关心发生了什么，也会追问原因、动机和细节。

旧货铺把这种好奇转换成玩法：用户先看到物，再通过问题走近人。未来的 AI 角色可在作品事实范围内回应不同提问，让同一个故事拥有不同的进入路径。产品要验证的，是这种主动交流是否能让用户更愿意读完、理解并讨论一篇故事。

### 5.2 为故事内容提供新的呈现载体

在取得创作者同意并完成内容适配后，一篇故事可被整理成“物件—角色—事实—场景—对话”的互动篇章。原作品保留清晰来源，互动体验负责提供新的阅读入口。

| 社区场景 | 可提供的价值 | 产品边界 |
| :--- | :--- | :--- |
| 故事或生活经历阅读 | 通过物件、场景和交流建立代入感 | 不将改编新增设定混同为原作者陈述 |
| 作者与读者交流 | 将反复出现的基础问题整理成角色知识，帮助读者理解作品 | AI 角色不冒充原作者，也不代替作者作事实承诺 |
| 围绕人物选择展开讨论 | 从“如果我是店主，会怎么做”引出读后讨论 | 讨论入口属于后续方案，当前未接入知乎评论系统 |
| 优质内容回顾 | 以旧物收藏册连接故事记忆与原文来源 | 当前收藏保存在本游戏中，不等同于知乎账号收藏 |

### 5.3 让看山成为故事的引路人

本项目选用看山作为来访角色，目的在于让其承担稳定的叙事连接：迎接玩家的好奇、介绍物件来历，并在故事结束后帮助玩家理解寄展的意义。

看山的价值需要通过实际互动建立，而不仅是出现在画面里。角色应保持身份一致、语气连贯，在不知道某个细节时承认未知，不为了维持对话而编造经历。

### 5.4 为创作者保留参与空间

长期可将篇章制作流程整理成创作模板：作者提供故事与使用范围，团队配置物件、角色和场景，系统协助检查事实一致性，并由创作者确认后发布。

这一方向的价值，是让内容生产与互动体验连接起来，而非无限生成故事。目前尚未建设作者后台、内容市场或知乎账户接入，相关部分属于后续验证方向。

## 六、技术方案

### 6.1 整体架构

```text
玩家浏览器
  └─ React + TypeScript：场景、交互、逐句阅读、声音、收藏册
       └─ HTTPS 同源 API
            └─ FastAPI：会话、剧情进度、问答、寄展与收藏
                 ├─ JSON 故事配置：角色身份、事实、正文、素材与规则
                 ├─ AIProvider：按当前剧情材料生成与审校角色回答
                 └─ SQLite：对话、进度、收藏快照与请求去重记录
```

| 模块 | 当前选型 | 选择理由 |
| :--- | :--- | :--- |
| 前端 | React、TypeScript、Vite | 便于组织场景与状态，快速迭代浏览器内体验 |
| 表现层 | 场景插图、角色图层、CSS 动态 | 在控制素材与运行成本的同时建立叙事氛围 |
| 音频 | 背景音乐、逐句预生成配音、浏览器播放控制 | 降低播放等待，支持重听、音量控制和阅读节奏协调 |
| 后端 | Python、FastAPI | 以清晰接口管理剧情与会话，便于对话模块接入 |
| 数据 | SQLite 单实例持久化 | 满足首版小规模试玩的部署与恢复需求 |
| 剧情 | 结构化 JSON 配置 | 将正文、身份、事实和展示顺序集中管理 |
| 部署 | 阿里云轻量服务器、Nginx、Docker | 使用团队已有资源，前端与 API 同源，数据库独立持久化 |

部署采用项目专用子域名。Nginx 提供 HTTPS 与前端静态文件，并将 API 请求转发到仅监听本机的后端服务。项目与服务器上的其他站点使用独立配置和数据目录。

### 6.2 AI 对话的职责与边界

设计目标是“有事实约束的角色交流”。后端根据当前阶段筛选角色可以知道的材料，再交给对话模块。模型返回台词与材料引用，经过独立审校后交付玩家；推荐问题来自当前阶段的剧情配置。看山对话模块不产生收藏或推进剧情的操作。

例如，故事开始前，看山可以解释自己受苏晚委托办理寄展，但不应提前透露照片人物的身份。玩家提出猜测时，系统也不能直接将猜测记为事实。

**当前已通过用户指定的 模型服务接入 `gemini-3.8-flash`（Gemini 原生协议），完成自由提问、缺失事实、阶段边界与无关问题测试。** 模块使用固定角色提示词、进度裁剪、材料引用与二次审校；无关问题统一回复“你问的好像和我们的物件无关哦，请换一个问题～”。这些措施降低偏题和编造概率，仍需持续用真实玩家提问检验。密钥仅保存在后端配置中。

### 6.3 剧情进度与恢复

游戏阶段由后端管理，覆盖阅读前、阅读中、阅读后与完成收藏。前端逐句上报推进动作，后端检查会话版本、播放轮次和单元顺序，防止重复点击或旧请求覆盖新进度。

写请求携带独立请求标识，重复请求可以返回已保存结果，降低网络重试带来的重复收藏或重复操作。会话凭据保存在当前浏览器，服务端保存其哈希。刷新页面后可以读取已保存进度；这不是跨账号、跨设备同步。

### 6.4 运行保障

系统已包含请求频率限制、并发调用上限、每日调用次数预算、会话有效期和数据库容量限制。SQLite 通过一致性备份方式保存数据，部署时需完成备份与恢复验证。

首版采用单实例，不将其描述为已经验证的大规模并发架构。后续是否引入集中式数据库、共享限流与对象存储，取决于实际试玩规模与资源瓶颈。

## 八、验证方式与评审体验建议

### 8.1 重点验证的问题

| 验证方向 | 观察方式 |
| :--- | :--- |
| 阅读是否舒适 | 观察玩家能否理解点击推进、完整显示、自动阅读与重听操作 |
| 故事是否具有吸引力 | 记录进入剧情后的完成率、主要退出位置和读后反馈 |
| 交流是否有价值 | 收集玩家真正想问的问题，区分已回答、未知和应在阅读后回答的问题 |
| 收藏是否形成情感收束 | 观察寄展确认与收藏册打开行为，询问玩家是否理解物件的意义 |
| 真实 AI 是否可靠 | 持续测试身份一致性、提前剧透、未知事实、超时重试和不当状态变更 |
| 部署是否稳定 | 检查素材加载、音频播放、刷新恢复、服务重启后进度及错误提示 |

这些指标是计划采用的验证方法，当前没有对外宣称用户规模、留存提升或商业转化数据。

### 8.2 建议评审路径

1. 进入店铺，查看相机，选择一个问题了解来意。
2. 点击“听听故事”，体验逐句阅读与场景切换；按需试用自动阅读、重听和记录。
3. 完成篇章后继续交流，独立确认接收寄展。
4. 查看展柜中的相机，打开收藏册，点击图案进入介绍与全文。
5. 刷新页面，验证已保存进度能够恢复。

本次作品希望首先证明：**一件旧物可以成为交流的起点，一段故事可以拥有可参与、可停留、可收藏的阅读方式。** 在此基础上，受约束的 AI 角色将进一步拓展用户主动提问的空间。
