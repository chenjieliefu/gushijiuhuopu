## 会话创建与恢复

1. 浏览器没有本项目的会话凭据时，调用 `POST /api/sessions`，无请求体也可。
2. 响应为 `{ "token": "...", "state": { ... } }`，HTTP 状态为 `201`。创建接口每次都生成新会话，不是“继续游戏”。
3. 建议先以带项目名前缀的 localStorage 键保存 token，满足同一浏览器继续；这部分需要前端保存，后端只负责验证凭据和恢复进度。
4. 后续请求增加 `Authorization: Bearer <token>`。本版本不用登录 Cookie，不必设置 `credentials: include`。
5. 刷新时有 token 就调用 `GET /api/session`；成功后恢复进度。网络失败和 `5xx` 显示重试，不自动新建会话。
6. `401` 时提示会话失效并提供重新开始入口。新旧会话之间比较版本号没有意义，切换会话时要清空前端旧状态。

不要将 token 放在 URL、报错截图或共享日志中。

## 路由与请求字段

所有写操作（创建会话除外）都包含 `request_id` 和 `expected_version`。

| 方法与路径 | 额外字段 | 用途 |
| --- | --- | --- |
| `GET /api/story` | 无 | 获取公开标题、物件名和可检查位置 |
| `POST /api/sessions` | 无 | 创建匿名会话 |
| `GET /api/session` | 无 | 读取当前进度、对话与收藏 |
| `POST /api/inspect` | `target_id` | 检查物件 |
| `POST /api/chat` | `message` | 提问，1 至 2000 字符 |
| `GET /api/pages/{page_id}` | 无 | 获取已解锁故事页正文 |
| `POST /api/pages/{page_id}/read` | 无 | 记录已读，不新增故事事实 |
| `POST /api/collection` | 无 | 玩家确认接收寄展 |
| `POST /api/reset` | `confirm: true` | 清空当前体验并重新开始 |

一次检查请求示例：

```json
{
  "request_id": "f2a5cd43-479e-41a4-badf-64c2b39c353a",
  "expected_version": 0,
  "target_id": "camera_front"
}
```

`request_id` 为 UUID，可在支持的浏览器环境用 `crypto.randomUUID()` 生成。`expected_version` 来自本会话最近一次服务端状态；首次为 0。

创建会话返回 `token + state`，其余成功的游戏写操作与 `GET /api/session` **直接返回 State**，不额外套 `state`。

## State 如何映射到界面

| 字段 | 前端用途 |
| --- | --- |
| `session_id/story_id/story_version` | 当前会话与内容版本标识 |
| `version` | 当前进度版本，用于写请求和避免旧响应覆盖新状态 |
| `status` | `active` 可探索；`completed` 展示来访结束和回顾入口 |
| `messages` | 服务端已保存的对话，每条为 `role/text`；当前没有消息 ID 或时间戳 |
| `clues` | 已检查线索，含 `id/text/source`，目前 source 仅为 `inspection` |
| `disclosed_facts` | 已披露事实 ID；不等于面向玩家的线索文案 |
| `summary` | 已披露事实摘要，目前不是专门设计的玩家界面文案 |
| `unlocked_pages` | 已解锁页面 ID，用于访问和新增提示 |
| `read_pages` | 已读页面 ID，与解锁分开 |
| `expression` | `neutral/thoughtful/warm`，需要与素材表情对应 |
| `suggested_questions` | 最多三个建议问题；开局允许为空 |
| `can_collect` | 控制“接收寄展”按钮；后端仍会再次校验 |
| `collection` | 未收藏为 `null`；已收藏含 `story_id/item_name/summary` |
| `is_test_fixture` | 标识测试章节，不是正式剧情 |

前端不按聊天轮数或关键词自行计算通关。对话成功后用完整 State 更新界面，避免把本地临时消息重复追加到服务端 messages。

## 等待、重试和版本冲突

| 场景 | 前端处理 |
| --- | --- |
| 正在回复 | 显示等待状态，暂时禁用重复发送和其他游戏写操作；本地浏览已加载内容不受影响 |
| 请求失败或响应丢失 | 保留玩家输入和整个原始请求；重试复用同一个 request_id、版本及内容 |
| `504 AI_TIMEOUT` / `502 AI_UNAVAILABLE` | 提示生成失败，可重试；不要清空会话 |
| `502 INVALID_AI_EVENT` | 进度未改变，保留输入，记录 trace_id 交后端排查，避免无限自动重试 |
| `409 VERSION_CONFLICT` | GET 最新进度，再判断用户动作是否还需要执行；需要时生成新 request_id |
| `409 IDEMPOTENCY_CONFLICT` | 同一 request_id 被用于不同内容，属于请求管理错误，先排查 |
| 旧响应晚到 | 同一会话只应用不低于当前 version 的响应，必要时 GET 最新状态 |
| `409 STORY_VERSION_CHANGED` | 提示内容已更新，得到玩家确认后 reset，不自动删除进度 |
| `409 TURN_LIMIT` | 当前测试会话达到 100 轮上限，提供确认重置入口 |

后端默认 AI 等待上限为 10 秒；建议前端网络超时留出额外余量（例如先用 15 秒），最终按真实模型耗时再定。前端超时不代表后端一定没完成提交，因此重试必须复用原请求。

错误结构统一为：

```json
{
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "进度已更新，请重新读取后再操作",
    "trace_id": "服务端追踪 ID"
  }
}
```

## 故事页、接收和重新开始

**故事页：**比较前后 `unlocked_pages`，仅对新增 ID 提示；请求完成后展示提示，不重复打断输入。玩家打开时 GET 正文，实际呈现后再调用 `/read`。GET 不标记已读；`read` 也不等于披露新事实。若产品要求页面首次揭示秘密，需另行扩展展示确认，不能自行把整个故事标为已披露。

**接收寄展：**`can_collect=true` 后显示按钮。先显示确认提示“接收后，本次来访将结束；你仍可回顾已发现的故事”，玩家确认后才 POST `/api/collection`。收到 `completed` 和收藏数据后再表现告别、入架动效。动画跳过或刷新不再创建第二条收藏。

**重新开始：**先提示会清空当前体验的对话、线索与收藏，确认后 POST `/api/reset` 并传 `confirm:true`。沿用当前 token，使用服务端返回的新状态；version 持续增长，不归零。当前重置保留历史请求去重记录，不是隐私数据删除功能。

## 第一轮实际联调路径

每一行写操作用新的 request_id；正常顺序中版本如下：

| 步骤 | 操作 | 写入时 expected_version | 成功后的关键状态 |
| --- | --- | --- | --- |
| 1 | 创建会话 | 不需要 | version=0，保存 token |
| 2 | inspect `camera_front` | 0 | version=1，有第一条线索 |
| 3 | chat 任意非空问题 | 1 | version=2，有 `demo_origin` |
| 4 | inspect `photo_back` | 2 | version=3，有第二条线索 |
| 5 | chat 任意非空问题 | 3 | version=4，解锁 `demo_page`，can_collect=true |
| 6 | GET `demo_page`，然后标记 read | 4（仅 read） | version=5，已读记录保存 |
| 7 | 确认后 collection | 5 | version=6，status=completed |
| 8 | 刷新后 GET session | 不需要 | 恢复同一收藏和完成状态 |

再测四个异常：双击收藏、回复超时后重试、旧响应晚于新响应、重置后旧请求重发。预期是不重复收藏、不丢进度、不退回旧状态。
